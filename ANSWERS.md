1. What holds the fleet's current state in your backend, and why that shape, given it has to serve
both the WebSocket stream and the polling endpoint consistently?
ANS = Fleet state lives in state.py as a plain dict[robot_id, entry]. A list indexed by robot number was considered and rejected: MQTT messages identify robots by robot_id (a string), not by array position, so a list would need a separate robot_id → index map just to know which slot to update — meaning you'd maintain two structures to do what one dict already does.

The consistency requirement — REST and WebSocket must never disagree — is handled two ways. get_snapshot() (used by the /fleet REST endpoint) returns an independent copy of fleet_state, not a live reference, so a REST response reflects one single point in time rather than risking a torn read where some robots are serialized with old values and others with values updated mid-serialization. On the WebSocket side, ConnectionManager.connect() immediately seeds a new client's queue with a full snapshot before any deltas are sent — without this, a client would start with zero knowledge of any robot and would only learn about each one whenever it next happened to publish, potentially several seconds later. After the snapshot, broadcast() sends incremental deltas, so both REST and WebSocket are always derived from the same underlying fleet_state, just accessed differently (pull a copy vs. push a stream).

2. Name one real tradeoff you made: the mechanism you chose for robots to reach your backend,
its delivery guarantees, and how you reconcile that mechanism's semantics with your
WebSocket fanout. Argue for the decision, including its cost.

ANS= Robots publish to the backend over MQTT (Mosquitto), not Kafka, RabbitMQ, or Redis pub/sub. Kafka's durable multi-consumer replay model is built for a scale and use case this project doesn't have — one consumer (the backend), no need to replay history, only current state — so its broker/partition/retention infrastructure would be pure overhead. RabbitMQ and Redis pub/sub are both fire-and-forget: a new or reconnecting subscriber gets nothing published before it subscribed, so "last known state" would have to be hand-built as a separate cache. MQTT's retain=True gives that behavior for free — any subscriber, new or reconnecting, immediately gets each robot's last published value.

Delivery guarantee: QoS 1 (at-least-once). State updates are idempotent — a duplicate delivery just overwrites fleet_state[robot_id] with the same value, which is harmless — while QoS 0 risks silently dropping an update, which is worse. QoS 2's exactly-once guarantee solves a duplication problem this system doesn't actually have, at the cost of extra handshake overhead per message.

Reconciling this with WebSocket fanout: QoS 1 means the backend's MQTT consumer could occasionally receive the same update twice. Because update_robot() just overwrites the entry for that robot_id, a duplicate produces the same fleet_state either way, and broadcast() sends it to WebSocket clients as another delta — at worst a client sees one redundant, identical delta, never stale or conflicting data. The cost of this choice is that this reasoning about idempotency is what makes QoS 1 safe here — if updates were not naturally overwrite-safe (e.g. if they were increments/counters), QoS 1's duplicates would silently corrupt state, and a different mechanism or dedup logic would be required.

3. What did you leave out, and what would you build next given more time?
ANS=
Left out: MQTT reconnect handling — mqtt_consumer.py doesn't currently wire up on_disconnect with auto-reconnect, so a mid-run broker drop would require a manual restart of the backend rather than recovering on its own. There's also no schema validation on incoming MQTT payloads; the backend trusts the shape of the data because it's produced by our own publishers, ...but this wouldn't hold up against malformed or unexpected input. update_robot() also overwrites fleet_state[robot_id] unconditionally, with no check against the timestamp already stored — so an out-of-order message (an older update delayed behind a newer one) could briefly make a robot appear to jump backward in position or battery level. The optional persisted-history endpoint (GET /robots/history/{robot_id}) wasn't attempted given the timebox.

Given more time, the first thing I'd build is the MQTT reconnect logic, since it's the most realistic failure mode given the brief's emphasis on flaky networks. Second, I'd add a timestamp check in update_robot() to reject out-of-order messages, since it's a small, targeted fix for a real correctness gap. Third, I'd add the persisted-history endpoint — update_robot() already returns each new entry, so a history store could plug in as a third consumer of that return value without touching state.py or connection_manager.py. Fourth, I'd act on last_updated, which is already stored but unused — a periodic sweep marking robots "stale" past some threshold, surfaced via REST/WebSocket, so a downed robot doesn't just silently stop updating with no signal to the dashboard.
